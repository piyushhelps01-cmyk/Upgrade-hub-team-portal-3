## Release acceptance rule

Do not mark a requirement complete solely because there is a module card, schema field or route. For each control, verify the actual behaviour for permitted and denied roles, record a test result/evidence link, name an owner and review date, and obtain the relevant sign-off. The checklist is intentionally `Not run` until that work is recorded.


## v4.0 expansion status

The catalogue now has **67 named module workspaces and 67 structured schemas**. The new workspaces include departments/org structure, capacity planning, shift planning, OKR cycles, surveys, recognition, communication templates, service catalog/SLA, purchase orders, expenses, budgets, client accounts, customer feedback, sprint planning, QA test cases, bug tracking, code review register, release calendar, API registry, secret-rotation metadata, data retention, legal holds, notification rules, scheduled reports, event calendar and digital member ID metadata.

These additional areas use the common record engine unless a specialised service is explicitly listed. Presence in the catalogue does not imply end-to-end workflows for financial ledgering, QR issuance, survey anonymisation, MFA, external notifications, legal-hold enforcement, secret vault rotation, scheduled reporting or automated retention. The 732-control acceptance checklist intentionally separates the new requirements from completed source-level checks. All new rows remain `Not run`.
